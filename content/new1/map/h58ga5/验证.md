# 验证记录

**这份表的用途只有一个：别重复验。**

下面每一条都是**真机/真构建**跑过的，带日期和怎么验的。改动没碰到的部分，
默认它还是好的 —— 不要每次开新会话就重跑一遍（尤其不要为了「确认一下」去截图、
起窗口、跑压测），那是纯浪费。

**例外**：用户主动说「重新验一下」。或者你**动了它依赖的那段代码** ——
那种情况请在本表里找到对应条目，改完后把它标成 `⚠️ 已失效（改了 X，待复验）`，
再验一次并更新日期。

还没验过的写在最后一张表，别混进来。

### 2026-11-10 · 流式性能

压测台 `examples/mdstream`（`PROSE` / `CODE` / `SECTIONS` / `NOHL` / `INTERVAL` 五个开关）。
release 构建、每次 12 秒、采样进程 CPU 时间；同机同构建，前后可复现。

| 场景 | 修之前 | 修之后 |
| --- | --- | --- |
| 长代码块一路长大（最常见的长回复） | 跑满一个核 · 15 帧/秒 · 帧间隔 65ms · 峰值 88ms | 25% 核 · 60 帧/秒 · 16.7ms · 峰值 40ms |
| 散文 3000 字（一个代码块） | 3.0s CPU / 12s | 1.2s CPU / 12s |
| 极端：每 200 字一个代码块 + 表格 | 7.6s CPU / 12s | 2.4s CPU / 12s |

顺带验过的两件事：
- **高亮器必须只造一次**（`OnceLock`）—— 否则每帧反序列化语法集，就是上表「修之前」那一列。
- **缓存键不能是整段内容的哈希** —— 流式时永远命不中，且表无上限会一直涨（泄漏）。
  单测盯住了：同内容拿同一个 `Arc`、缓存不超 64 条。
- **把合帧间隔 16ms 放宽到 50ms 省不下 CPU**（3.25s vs 3.03s，噪声内）。代价在
  「内容一变就重新解析」，跟帧率无关。**别再往这个方向优化了。**

## 环境上的两个已知怪事（不是产品 bug）

- `.github/workflows` 只跑 `cargo test -p nous-engine` 和 release 构建，**不跑** examples，
  所以 CI 不会撞下面这条。
- 本机 `cargo test -p nousdesk` 偶发报 `can't find crate for gpui_kit` /
  `metadata stub` —— 只在 examples 还没编过时出现（`#[path] "../src/md.rs"` 的副作用）。
  先 `cargo build -p nousdesk --example mdpreview` 编一遍例程，再跑 test 就好。
- 窗口截图：`~/shotpid.ps1 -id <pid> -out <png>`（按 PID 找窗口、先 SW_RESTORE，
  最小化的窗口 `GetWindowRect` 是 -32000 / 黑图）。装了 D3D 的窗口要顶到前台再截。
