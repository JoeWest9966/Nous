# 坑

每踩一个就往这儿加一条。**症状 → 根因 → 怎么解**，三行以内，别写成日记。
加新条目往**末尾**追加，编号顺延。

---

## 1 · rustc 1.88 编不过

**症状**：`cargo check` 报 `rustc 1.88.0 is not supported by the following packages`
（cosmic-text / oo7 / ordered-float 要 1.89~1.92）。
**根因**：GPUI 依赖链的下限已经跑到 1.9x。
**解**：`rust-toolchain.toml` 写 `channel = "stable"`，别钉死小版本。

## 2 · Xvfb 上窗口全黑，无任何报错

**症状**：进程活着、渲染循环在跑（strace 看到 14ms 一次的 timerfd），截图纯黑，日志干净。
**根因**：mesa 22.3.6（bookworm 默认）的 llvmpipe Vulkan WSI 有 bug，swapchain 的
present 不落到窗口。注意 `vkcube` 可能**能画**（24 位窗口），别被它误导。
**解**：装 bookworm-backports 的 mesa ≥ 25.0.7。

## 3 · 有 Vulkan 也画不出来：缺 compositor

**症状**：升了 mesa 之后仍没有画面。
**根因**：GPUI 用 **depth 32 带 alpha** 的 Visual；X 没有 compositor 时，32 位窗口的
present 没有人合成，静默黑屏。
**解**：`picom --backend xrender` 跑起来。日志里 `x11: compositor present: false` 是线索。

## 4 · GPUI 的 log 全被吞掉

**症状**：黑屏但 `RUST_LOG=trace` 一点输出都没有，完全没法查。
**根因**：GPUI 不装全局 logger，`log` crate 的宏在没人 `set_boxed_logger` 时是空操作。
**解**：`main.rs` 里自己装个最简 stderr logger（见 `crates/nous-desktop/src/main.rs`）。
装完之后 `Selected GPU adapter` 这类关键日志才会出来。

## 5 · `CARGO_TARGET_DIR` 指向别的项目

**症状**：`cargo build` 成功，但 `./target/debug/nous-desktop` 不存在。
**根因**：这台机器全局环境变量 `CARGO_TARGET_DIR=/opt/Warehousetui/target`。
**解**：二进制去 `$CARGO_TARGET_DIR/debug/` 找，或者 `unset CARGO_TARGET_DIR`。

## 6 · 引擎返回 camelCase，serde 按 snake_case 解析

**症状**：`/v1/sessions` 解析失败：`missing field 'read_only'`。
**根因**：给类型写了 `pub read_only` 但没加 `#[serde(rename_all = "camelCase")]`。
**解**：每个描述引擎响应的 struct 都要带 `rename_all = "camelCase"`。
**测试兜住**：`crates/nous-engine/tests/parse.rs` 用真实 JSON 做反序列化，改字段先跑它。

## 7 · `text` 字段会是 `null`（踩了两次）

**症状**：`invalid type: null, expected a string`，位置分别在 `sessions[].last.text`
和 `entries[].text`。
**根因**：引擎对「有 entry 但没正文」的情况（空回复的 assistant）给 `text: null`。
**解**：所有文本字段一律 `Option<String>`，渲染时 `unwrap_or_default()`。
**通则**：引擎那边**任何**字符串字段都当可 null 处理，只有 `kind` / `id` / `name` 例外。

## 8 · GPUI 的 executor 不是 tokio

**症状**：`cx.spawn` 里直接 `.await` reqwest，跑不起来 / 卡住。
**根因**：GPUI 有自己的 executor，reqwest 要 tokio 的 IO driver。
**解**：`main` 里起一个 tokio runtime，Handle 存 `static TOKIO`；UI 里
`crate::TOKIO.get().unwrap().spawn(..).await` 拿到结果，再 `this.update(cx, …)` 回传。

## 9 · `on_click` 在 `Div` 上不存在

**症状**：`no method named 'on_click' found for struct 'gpui_kit::Div'`。
**根因**：`on_click` 定义在 `StatefulInteractiveElement` 上，而它只实现给
`Stateful<E>`。`div()` 返回裸 `Div`。
**解**：链式里先 `.id(...)` —— 那是唯一把 `Div` 转成 `Stateful<Div>` 的入口。
**别试**：`use StatefulInteractiveElement` 单独导入没用，类型上就没有这个方法。
**同一个坑的其它成员**：`overflow_y_scroll` / `track_scroll` / `hover` 之类也长在
`Stateful<Div>` 上。要滚动就 `.id("x").overflow_y_scroll().track_scroll(&handle)`。

## 10 · 两套 Div：`gpui-component` 和 gpui 原生

**症状**：`h_flex()` / `v_flex()` 有一堆样式方法（`bg`/`p_3`/`gap_2`），但死活没有
交互方法；换成 gpui 原生 `div()` 又反过来。
**根因**：`gpui-component` 的 `h_flex`/`v_flex` 是它自己的 `Div`（带 `StyledExt`），
和 gpui 的 `Div` 是两个类型。混用就会撞墙。
**解**：本项目统一用 **gpui 原生** `div().flex().flex_col()` + `px()` / `p()`，
不用 component 的 `h_flex`/`v_flex`。

## 11 · `pgrep -f` 把自己杀了

**症状**：`pkill -f nous-desktop` 之后当前 shell 命令直接退出（exit 143），后续命令没跑。
**根因**：`-f` 匹配整个命令行，**包括正在执行这条 `pkill` 的 shell 自己**。
**解**：用 `pkill -x nous-desktop`（精确匹配进程名）。

## 12 · 截图截到黑屏，其实是程序已经退出

**症状**：`timeout 6 vkcube & import -window root` 截出来纯黑，以为渲染坏了。
**根因**：`timeout` 到期把窗口关了，截的是空 root。
**解**：后台起进程 → `sleep` → 截图 → 再 `kill`。顺序别颠倒。

## 13 · SSE 的 `changes[]` 类型不止 `text_delta`

**症状**：能发消息，气泡半天不出字；或者只出后半段（开头被吞）。
**根因**：除了 `text_delta` 还有 `text_start`（块开头，`block.text` 已经是全文）、
`thinking_delta`（思考）、`toolcall_delta`、`block`、`message`。
只在 `text_delta` 上拼字符串就会漏掉第一段。
**解**：全集看 `@earendil-works/pi-durable/dist/harness/events.d.ts` 的 `MessageChange`，
照抄，不认识的走 `#[serde(other)]`。`thinking_*` 不进气泡。

## 14 · 会话列表按 id 升序，聊天应用要反的

**症状**：新会话总在最下面，滚半天找不到。
**根因**：引擎 `GET /v1/sessions` 按 id 升序给，它不认识「聊天应用」这个偏好。
**解**：客户端拉完 `sort_by(|a,b| b.id.cmp(&a.id))`。这是**这一页的事**，别去改引擎。

## 15 · `xdotool type` 打中文会丢字

**症状**：脚本里 `xdotool type "从一数到五"`，界面上变成「从数到五」。
**根因**：xdotool 逐键发 keysym，CJK 靠输入法，字符容易掉。
**解**：验中文输入只在**装好的 Windows/真机**上做；headless 截图里别拿 CJK 当断言。

## 16 · SSE 长连接被「10 秒总超时」掐断

**症状**：回答跑过十来秒必断，界面弹 `生成失败：HTTP 流断了: error decoding response body`，
可引擎那边还在正常生成（`busy: running`、entries 还在长）。
**根因**：普通 JSON 请求和 SSE 共用一个 `Client::builder().timeout(10s)`；reqwest 的
`timeout` 是**整个请求**的超时（含读 body），不是「多久算超时」的心跳阈值。
**解**：SSE 单独一个 client，只给 `connect_timeout` + `read_timeout`（空闲读），**不给总超时**。
见 `crates/nous-engine/src/client.rs`。

## 17 · 用户按「停止」也会把 SSE 掐断，那不是失败

**症状**：点完「停止」界面弹红条「重试 / 收起 HTTP 流断了」，看着像出错了。
**根因**：abort 让引擎关流，客户端读流照样报错，和真失败共用 `live.fail` 一条通道。
**解**：`send()` 复位、`stop_generation()` 置位 `user_stopped`；那一轮的流错误只写日志
（`停止后流断开，按预期忽略`），不进 `turn_error`。

## 18 · 长文字会把右端的兄弟元素顶出屏幕

**症状**：红条右侧的「重试 / 收起」整颗消失 —— 不是被遮挡，是没排进来。
**根因**：`flex_1` 里不换行的文字按**内容宽度**算最小宽度，`min_w(0.)` / `overflow_hidden` /
`text_ellipsis` 都拦不住它把右边的兄弟推出去。
**解**：动作按钮**左锚**、长文字放最后（`[重试][收起] 正文…`）；别把按钮放在长文字右边。

## 19 · `TextareaState` 的回车默认是「插换行」

**症状**：多行输入框里按回车像是发送了，但发送失败/被拦下时输入框里留下一个空行。
**根因**：`submit_on_enter` 默认 `false`，`enter()` 里 `insert_newline = is_multi_line && (!submit_on_enter || shift)`。
**解**：构造时 `.submit_on_enter(true)`；Shift+回车仍然换行（走 `shift` 分支）。

## 20 · `gpui_kit::assets::Assets` 只有 106 个图标，别的一律「静静地不画」

**症状**：代码写了 `IconName::Paperclip`，编译通过、运行无报错，界面上什么都没有。
**根因**：默认 `Assets` 是给组件自用的一份**子集**（106 个），全量 1830 个在 `AllAssets`。
**解**：`application().with_assets(gpui_kit::assets::AllAssets)`（+2.8MB）。图标名写错也不会报错。

## 21 · 直接 `.child(IconName::X)` 用的是「窗口默认文字样式」

**症状**：浅色背景上的图标完全看不见（本项目的窗口默认文字是白字）。
**根因**：`IconName` 的 `RenderOnce` 取 `window.text_style()` 的颜色和字号，**不继承父 div** 的
`text_color` / `text_size`。
**解**：`Icon::new(x).text_color(rgb(0x5a5a5a)).size(px(18.))` 自己给。
