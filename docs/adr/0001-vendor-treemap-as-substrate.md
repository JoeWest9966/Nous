# 0001. 用 vendoring 接住 Treemap，不当 fork 用

- 状态：已接受
- 日期：2026-10-26
- 基线：`Treemap@8e208e3`

## 背景

Nous 的骨架（节点树、squarified 布局、走一手的 `Move` 日志、带 409 的乐观写盘、token 与动效）
在 Treemap 里已经写过一遍并且跑通了。重写一遍骨架换不来任何东西，只会把已经踩过的坑再踩一遍。

同时，Nous 是**另一个产品**，不是 Treemap 的下一版。两者迟早会在同一批文件里给出相反的答案：
棋盘怎么摆、节点是什么、谁来写盘。真到了那一步，一个能 `git merge` 的上游就从资产变成债务 ——
每次同步都要在别人的假设上重新做一遍自己的决定。

## 决定

新仓库，**不是 GitHub fork**（不用 Fork 按钮，不落在同一个 fork network 里）。
历史照搬，上游挂在 `treemap-upstream` 这个 remote 上**只读**。

- 需要上游某个改动：读 diff，手动重打一遍。**不 merge、不 rebase、不 cherry-pick 整段。**
- 判断标准很简单：这段代码进 Nous 时，你是否愿意为它做一次自己的决定？
  愿意 → 搬；不愿意 → 说明它本来就该留在 Treemap。
- 上游从此冻结在基线那一刻。它是一件**参考实现**，不是一条要追的分支。

## 后果

- 好处：任何一行代码进 Nous 都经过了「这真是 Nous 的东西吗」这一问。分叉是显式的，不是意外。
- 好处：没有 `origin/main` 的 pull 诱因，不会某天顺手 `git pull` 把 Treemap 的假设请回家里。
- 代价：上游的 bugfix 不会自动过来。接受 —— Nous 要改的正是这些地方。
- 代价：`src/` 里会长期存在两套词汇（棋盘的「块 / 组」和 Nous 的领域词）。
  用 `GLOSSARY.md` 划界，搬过一次就改一次名，别留着两套说法混着说。
